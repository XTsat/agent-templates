# AGENTS.md — Next.js Web 应用模板

> 本文件是任何 AI 编码代理（agent）进入 **Next.js Web 应用项目** 时的**必读**工作说明书。
> 它约定项目的架构、UI 规范、国际化、文档维护规则。任何对代码、配置、行为的改动，都必须同时遵守本文档的规则。
>
> 适用项目：基于 Next.js + React + TypeScript + Tailwind CSS 的 Web 应用。
>
> **来源**：本文件是 [agent-templates](https://github.com/XTsat/agent-templates) 的 `templates/nextjs-webapp/AGENTS.md` 副本，最新版见该仓库 `main` 分支。
> 用户说「更新 AGENTS」时按此流程：① 拉取来源模板最新版 → ② 与本地逐节比对 → ③ 合并（保留本项目已回填的项目名、目录结构、环境变量与项目特有约定）→ ④ 展示 diff 与改动清单，等用户确认后再落盘。**禁止整文件覆盖**。

## 1. 项目概览

**Next.js Web 应用** — 基于 Next.js 框架的全栈 Web 应用，支持 React 服务端组件与客户端组件、国际化、API 路由。核心技术栈：

- **框架**：Next.js（App Router）
- **语言**：TypeScript 严格模式
- **样式**：Tailwind CSS（v4，`@import "tailwindcss"`）+ `cn()` 工具函数
- **组件库**：shadcn/ui 风格（Radix UI + CVA + `cn()`）
- **国际化**：next-intl（或类似方案）
- **包管理**：pnpm

## 3. 技术栈与依赖

- **Next.js**：最新稳定版（App Router）
- **React**：19+
- **TypeScript**：严格模式，**禁止** `any`、`@ts-ignore`、`@ts-expect-error`
- **Tailwind CSS**：v4（`@import "tailwindcss"`），**禁止** v3 的 `tailwind.config` 扩展写法
- **组件库**：shadcn/ui 风格（Radix Primitive + `forwardRef` + CVA `variant`/`size` 变体）
- **国际化**：next-intl（`useTranslations('Namespace')` 或 `getTranslations`）
- **动效**：只使用 `tailwindcss-animate` / CSS transition，不引入新的动效库
- **包管理**：pnpm
- **类名合并**：统一使用 `@/lib/utils` 中的 `cn()`，禁止字符串拼接

## 4. 核心代码规范

### 4.1 样式统一规范

#### 组件使用规则

- **尽量复用** `src/components/ui/` 中的现有组件（Button / Card / Input / Badge / Dialog / Select 等）与既有页面写法，保持整体风格一致
- 若决定**新建基础组件或更改现有组件/页面写法**，必须先向用户询问确认，再动手实现
- 新 UI 组件建在 `src/components/ui/` 下时，风格对齐现有 shadcn/ui 模式（Radix Primitive + `forwardRef` + CVA `variant`/`size` 变体）

#### Tailwind 与样式写法

- 类名合并一律使用 `@/lib/utils` 中的 `cn()`，禁止字符串拼接
- 主题色、圆角、字体全部取自 `src/app/globals.css` 中的 `@theme` 变量（`--color-primary`、`--radius` 等），**禁止**硬编码十六进制颜色或魔数圆角
- 颜色语义化：`primary` / `muted` / `destructive` / `border` / `card` 等，按 Tailwind 语义类（`bg-primary`、`text-muted-foreground`、`border-border`）使用

### 4.2 国际化（i18n）规则

- **所有页面的文本都必须双语言**：任何面向用户的文案（页面标题、按钮、提示、错误信息、占位符等）必须同时提供中文与英文，**禁止**只写单一语言或硬编码文案到组件里
- 文案统一走 next-intl：`useTranslations('Namespace')` 或 `getTranslations`，禁止把中英文写死在组件中
- 新增文案必须**同步**修改两个语言文件，键名保持一致（camelCase），两个文件缺一不可
- 页面/区块文案按命名空间组织（如 `HomePage`、`RankPage`），新功能追加到对应命名空间，不新建碎片命名空间
- 修改语言文件后必须用 `tsc --noEmit` / `pnpm build` 校验 key 类型

### 4.3 代码风格

- TypeScript 严格模式，**禁止** `any`、`@ts-ignore`、`@ts-expect-error`
- 函数组件 + Hook，统一单引号、行尾无分号（与现有代码一致），格式化以 ESLint/Prettier 配置为准
- 文件组织遵循现有目录：页面 `src/app/[locale]/...`、业务组件 `src/components/`、工具 `src/lib/`
- **修改涉及多文件时，必须检查并遵循相邻相似文件的既有写法，保持整体一致性**

### 4.4 注释规范

- 注释规范见第 5 章「文档维护规范」的 [5.3 注释规范](#53-注释规范)

## 5. 文档维护规范（强制，不可省略）

### 5.1 CHANGELOG 维护

#### 流程

- 日常改动先记在 `## [Unreleased]` 段（顶部固定）。**发版时**再把内容移动到带版本号的新段。
- **先记后合**：记录阶段同一工作周期内的改动各自独立记入 `[Unreleased]`（同一功能的多处调整也先各记一条，避免遗漏）；提交或发版前的整理阶段统一过一遍 `[Unreleased]`，把描述同一件事的多条合并成一条，不相关改动保持独立（判断标准：用户会不会把它当成同一件事，细则见下方「写作视角」）。

#### 格式

统一使用 **扁平前缀式**：

```markdown
# Changelog

## [Unreleased]

> 一句话总结这个版本（可选）

- 新增：功能 A
- 修复：问题 B
- 变更：行为 C

## v0.3.0 (2026-07-06)

> 一句话总结这个版本（可选）

- 新增：功能 D
```

前缀分类：`新增` / `修复` / `变更` / `移除` / `性能`

**加粗规则**：条目默认不加粗；写 changelog 时先识别本次改动中的**重点改动**（核心新功能、重要修复、破坏性变更等），只对重点改动用 `**加粗**` 强调，其余条目一律不加粗。

**版本总结**：版本标题（`## [Unreleased]` / `## vX.Y.Z (YYYY-MM-DD)`）与条目列表之间，可加一行 `> 引用` 形式的一句话总结（概括该版本/该批改动的主旨），可选，不强制。

> 若 changelog 是在页面中渲染的（如 `src/app/[locale]/changelog/page.tsx`），则 changelog 变更需要 **三处同步**：页面 `entries` 数组最上方新增记录 + `messages/zh-CN.json` 新增文案键 + `messages/en.json` 新增同键名英文条目。

#### 写作视角（面向用户）

CHANGELOG 的读者是**网站使用者**，不是开发者。条目只写「用户能感知到的变化」，不写内部实现：

- **写用户视角的结果**：页面上能做什么、看到什么、行为/文案/默认值有什么不同。
- **禁止内部实现细节**：组件拆分、状态管理、数据结构、请求与缓存策略、埋点、依赖升级、重构过程，一律不写。
- **禁止出现代码标识符与文件路径**（如 `RankFilter`、`src/components/rank.tsx`）；用户直接接触的**页面名、按钮名、配置项 key** 除外。
- **无用户感知的改动不记入 CHANGELOG**：纯内部重构、样式微调、格式化、注释与测试调整等，写了用户也读不懂、也用不上。
- **只写相对上一版的变化**：每条回答「这个版本和用户手上的版本比，变了什么」，只讲差异；不复述仍然有效的旧功能，不写「继续优化」「体验更好」这类没有信息量的空话。
- **同一个变化合并成一条**：同一功能的多处调整、跨多个提交的同一件事，在提交或发版前的整理阶段合并为一条；同一内容不要在不同分类或不同版本段里重复出现。
- **一句话说清改了什么**：按「做了什么 + 用户得到什么」写完，不加背景、动机与实现过程，也不用复杂形容；用户扫一眼就能对上自己关心的功能。
- 判断标准：使用者读完一条，能判断「这次更新对我有什么不同」。

正反例：

```markdown
- ✅ 新增：排行榜支持按分数/时间筛选
- ❌ 新增 `RankFilter` 组件并改用 useMemo 缓存排序结果
- ✅ 修复：移动端榜单表格横向溢出
- ❌ 修复：`useEffect` 依赖数组缺失导致的重复请求
```

#### 版本号（准备发布时才确认）

- **日常开发不碰版本号**：只往 `[Unreleased]` 追加条目，`package.json` 的 `version` 保持原值；每个功能、每个修复各自是一次独立提交，提交里不带版本号变更，也不改辅助位置的版本字样。
- **准备发布时才确认并递增一次**：一次发版汇总了多个独立的功能/修复提交，等合并到指定版本、把 `[Unreleased]` 内容移入 `## vX.Y.Z (YYYY-MM-DD)` 的同一次操作里，才确认版本号（SemVer 见 6.2）、写进下方的**唯一版本源文件**、把辅助位置同步成同一个版本号并打 `git tag vX.Y.Z`。**不能每改一点就递增**——否则版本号会随提交次数突进，与实际发布节奏脱节。
- **唯一版本源**：`package.json` 的 `version` 字段。页面上需要展示版本时从它读取（构建时注入），不手写。

| 版本源文件 | 位置 |
|------|------|
| `package.json` | `version` 字段 |

下列位置属于**辅助信息，不是版本源**，不决定版本号（页面上需要展示版本时从 `package.json` 的 `version` 读取，构建时注入，不手写）：README 徽章、页面/文档正文里的版本字样、`messages/*.json` 中的版本文案。**日常提交不动它们；准备发布时必须逐个同步到同一个新版本号**，不得残留旧版本号或自相矛盾的版本字样；也不要新增此类重复版本号。为 changelog 条目新增的 i18n 文案 key 属于上面的 changelog 渲染规则，与本节的版本号同步无关。

#### 多会话并行开发

**⚠️ 更新 `CHANGELOG.md` 前必须先读取当前文件内容**，识别并保留其他会话已写入的既有条目（含 `[Unreleased]` 下未提交的功能），只追加自己的条目，**严禁整文件覆盖或删除他人记录**。

### 5.2 README 维护

#### 写作视角（面向用户）

README 的读者是**使用者**（站点访问者、部署者），不是开发者。只写使用者能直接用到的东西：

- **该写的**：这个应用是做什么的、有哪些页面/功能、怎么部署与配置环境变量、出问题怎么办。
- **不该写的**：实现原理与设计理念、组件与目录分层、状态管理与请求流程、算法、内部组件名/文件路径、性能优化手段、依赖内部实现。
- **代码只贴使用者要用的最小片段**：安装、构建、启动命令与环境变量示例；不贴内部实现代码。
- **技术细节翻译成使用者语言**：不写「用 `useMemo` 缓存排序结果」，写「榜单筛选切换即时生效」。
- 判断标准：使用者只读 README，就能独立完成部署 → 配置 → 使用 → 排障。

正反例：

```markdown
- ✅ 排行榜支持按分数/时间筛选
- ❌ `RankPage` 用 `useMemo` 缓存排序结果，数据经 SWR 缓存后注入 `RankFilter`
```

#### 双语文档同步

如果项目维护多个语言的 README（如 `README.md` + `README_en.md`），任何修改必须两文件同步：

- **中文为主（单向同步）**：中文版（`README.md`）是**权威版本（源）**，英文版（`README_en.md`）跟随中文版。所有改动**先落中文版，再从中文同步到英文版**；**禁止反向**——不得先改英文版再回填中文，不得用英文版覆盖中文版。
- 章节结构必须保持一致，新增章节两个文件都要加
- 中文版使用自然中文，英文版使用地道英文，**禁止**逐字机翻、禁止留下半翻译的句子
- 修改时逐条 diff，确保无内容遗漏或错位
- **禁止无意义的换行**：正文长句不要人为软换行（一段文字保持一行，由 Markdown 自动折行显示）；空行只用于分隔标题、表格、列表、代码块等结构性区块
- **多会话并行修改**：更新 README 前必须先读取当前文件内容，识别并保留其他会话已写入的既有内容，只追加/修改自己的部分，**严禁整文件覆盖或删除他人记录**

#### 何时必须更新 README

| 改动类型 | 必须更新的位置 |
|----------|--------------|
| 新增用户可见功能 | 功能列表 / 截图 |
| 修改快速开始步骤、部署方式、环境变量 | 快速开始章节 |
| 运行环境/依赖要求变化（如需要更高 Node 版本） | 快速开始（运行环境与依赖要求） |
| 项目定位/标语/链接变化 | 项目简介 |

**何时不需要更新 README：**
- 纯内部重构、样式调整、bug 修复（除非修复改变了用户可见行为）

### 5.3 注释规范

- **注释只写 non-obvious reason**：解释「为什么这么做」，而不是「做了什么」（代码本身应自文档化）
- **禁止残留 intermediate attempts**：不保留被注释掉的旧代码、TODO 但未完成的方案、调试输出

### 5.4 PR 描述规范

- **PR 描述只写最终行为**：描述最终完成了什么，而不是过程中尝试了什么
- 禁止提及：尝试过的方案、被否定的设计、从未合入的中间状态
- 只写 diff 里看不出来的取舍理由（如「选用方案A因为性能比B高20%」）

## 6. 提交与发布流程

### 6.1 提交规范

- 提交信息遵循 **Conventional Commits**：`<type>(<scope>): <中文短句式 subject>`（如 `feat: 排行榜页新增筛选`、`fix: 修复计分精度`、`docs: 更新快速开始`）
- **禁止**将未完成的功能、多轮迭代的中间状态、被废弃的方案写进提交信息
- **提交前必须先向用户展示，等用户确认后再执行 commit**，展示内容缺一不可：
  - 待提交文件清单
  - 改动概要（如 `git diff --stat`）
  - **提交标题，尽量给 2–3 个候选**（同一改动的不同侧重点：做了什么 / 为什么改 / 是否带 scope），逐条注明侧重供用户挑选并标出推荐项；确实只有一种合理写法时才只给一个
  - 用户选定标题（或自拟）后才 commit；涉及推送时另附提交 hash、提交信息、目标分支与改动概要
- 推荐顺序：完成功能代码 → 跑通验证 → 更新 CHANGELOG 与 README → 提交
- 文档更新与代码改动**在同一提交中完成**（不单独拆「补文档」提交）
- **推送（push）必须先经用户确认**：任何推送动作前必须向用户展示：提交 hash、提交信息、目标分支、改动内容概要；等待用户明确同意后再推送
- **授权一次性，不延续**（「上一轮说过推送」≠ 本轮可以提交）：
  - 用户的确认**只对当次动作生效**；下一次改动必须重新展示改动内容与提交标题，重新确认
  - 展示后改动内容又变了（用户提了新要求、你又改了文件，哪怕只改一行），**原确认立即失效**，必须重新展示并再次确认
  - 下列情形**都不算授权**：上一轮 / 上一个任务 / 上一个会话说过「提交」「推送」；会话恢复（resume / fork）后继承的历史授权；用户对功能或代码表示满意；用户正在讨论其它需求；用户未回复
  - 授权范围逐项独立：确认 commit ≠ 授权 push；确认推送某分支 ≠ 授权后续继续提交或推送；确认一个提交 ≠ 授权 `--amend` 或追加提交
  - 执行前自检：能指出用户**本轮**对**本次改动**的明确同意原话；指不出来就先问，不要执行

### 6.2 版本号规范

- 采用 **SemVer**：新功能 → `minor` 递增；bug 修复/小改进 → `patch` 递增
- **只在准备发布时递增**（规则见 5.1）：单个功能/修复提交不碰版本号；一次发版汇总多个独立提交、合并到指定版本时才确认版本号，改 `package.json` 的 `version`，并把 README 徽章、正文版本字样、`messages/*.json` 版本文案等辅助位置同步到同一版本号——逐次递增会让版本号突进
- 发版一致性：`package.json` version = CHANGELOG 新版本段号 = `git tag vX.Y.Z`，tag 推送同样需用户确认

### 6.3 构建验证

完成任何代码/文档修改后，运行验证：

```bash
pnpm build     # 构建 + 类型检查
```

确保无 TypeScript 错误、next-intl key 类型检查通过。

## 7. 最终检查清单（每次任务完成前）
