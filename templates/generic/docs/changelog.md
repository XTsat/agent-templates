## CHANGELOG 维护

#### 流程

- 日常改动先记在 `## [Unreleased]` 段（顶部固定）。**发版时**再把内容移动到带版本号的新段。
- **先记后合**：记录阶段同一工作周期内的改动各自独立记入 `[Unreleased]`（同一功能的多处调整也先各记一条，避免遗漏）；提交或发版前的整理阶段统一过一遍 `[Unreleased]`，把描述同一件事的多条合并成一条，不相关改动保持独立（判断标准：用户会不会把它当成同一件事，细则见下方「写作视角」）。
- **「上一版」= 上一次发布**：本文件所说的「上一版」指 `CHANGELOG.md` 中最新的 `## vX.Y.Z` 段，即使用者当前实际在用的版本；**不是上一个 commit、也不是 HEAD**。条目只需回答「这个版本和上一版比变了什么」，与中间经历过几次提交无关。
- **发版前被撤销的改动不留痕**：某改动只在 `[Unreleased]` 里记过、发版前又被移除时，整理阶段**删掉对应条目**即可，不写「新增后又移除」「已取消」「原计划作废」这类叙述——那是开发过程，不是使用者能感知的差异。`### 移除` 只用于删除**上一版已发布**过的功能（该情形属破坏性变更，按 SemVer 升 major/minor）。想在中间过程留痕就写 commit message（如 `revert: 移除 X`）和 PR 描述，CHANGELOG 不是 git log。
- **发版日期**：版本段日期 `(YYYY-MM-DD)` 填**当前日期**（以发版当天的系统时间为准）。

#### 格式

统一使用 **分组式**（与 scaffold 的 `CHANGELOG.md.template` 一致）：按分类用 `###` 子标题分组，条目用「标题 + 冒号 + 说明」，**仅重点条目/重点内容才加粗**：

```markdown
# Changelog

## [Unreleased]

> 一句话总结这个版本（可选）

### 新增
- 功能 A：说明
- **功能 B**：说明

### 修复
- 问题 C：说明

## v0.3.0 (2026-07-06)

> 一句话总结这个版本（可选）

### 新增
- 功能 D：说明
```

分组子标题分类：`新增` / `修复` / `变更` / `移除` / `性能`（只保留本次有内容的分类，无内容的分类不写空标题）。

**加粗规则**：条目默认不加粗；写 changelog 时先识别本次改动中的**重点改动**（核心新功能、重要修复、破坏性变更等），只对重点改动用 `**加粗**` 标题强调，其余条目一律不加粗。

**版本总结**：版本标题（`## [Unreleased]` / `## vX.Y.Z (YYYY-MM-DD)`）与分类子标题之间，可加一行 `> 引用` 形式的一句话总结（概括该版本/该批改动的主旨），可选，不强制。

#### 写作视角（面向使用者）

CHANGELOG 的读者是**使用者**（库的调用方 / CLI 用户 / 服务使用方），不是开发者。条目只写「使用者能感知到的变化」，不写内部实现：

- **写使用者视角的结果**：能做什么、输出/行为有什么不同、配置与默认值如何变化。
- **禁止内部实现细节**：模块与函数拆分、数据结构、算法、缓存与并发策略、日志埋点、依赖升级、重构过程，一律不写。
- **禁止出现代码标识符与文件路径**（如 `_load_config`、`src/core/parser.py`）；使用者直接接触的**命令名、参数名、配置项 key、公开 API 名**除外。
- **无使用者感知的改动不记入 CHANGELOG**：纯内部重构、格式化、注释与测试调整等，写了用户也读不懂、也用不上。
- **只写相对上一版的变化**：每条回答「这个版本和使用者手上的版本比，变了什么」，只讲差异；不复述仍然有效的旧功能，不写「继续优化」「体验更好」这类没有信息量的空话。
- **同一个变化合并成一条**：同一功能的多处调整、跨多个提交的同一件事，在提交或发版前的整理阶段合并为一条；同一内容不要在不同分类或不同版本段里重复出现。
- **一句话说清改了什么**：按「做了什么 + 使用者得到什么」写完，不加背景、动机与实现过程，也不用复杂形容；使用者扫一眼就能对上自己关心的功能。
- 判断标准：使用者读完一条，能决定「要不要升级、升级后有什么不同」。

正反例：

```markdown
### 新增
- ✅ 支持 `--timeout` 参数：自定义请求超时时间，默认 30 秒
- ❌ 新增 `_load_config` 并引入 dataclass 缓存，重构参数解析链路

### 修复
- ✅ 修复缺少参数时命令直接崩溃的问题
- ❌ 修复 `except` 分支未捕获 `KeyError` 导致的 `finally` 泄漏
```

#### 版本号（准备发布时才确认）

- **日常开发不碰版本号**：只往 `[Unreleased]` 追加条目，版本源文件里的版本号保持原值；每个功能、每个修复各自是一次独立提交，提交里不带版本号变更，也不改辅助位置的版本字样。
- **准备发布时才确认并递增一次**：一次发版汇总了多个独立的功能/修复提交，等合并到指定版本、把 `[Unreleased]` 内容移入 `## vX.Y.Z (YYYY-MM-DD)` 的同一次操作里，才确认版本号（SemVer 见 8.2）、写进下方的**唯一版本源文件**、把辅助位置同步成同一个版本号并打 `git tag vX.Y.Z`。**不能每改一点就递增**——否则版本号会随提交次数突进，与实际发布节奏脱节。
- **唯一版本源**：`{{ 版本号文件 }}` 的 version 字段（`pyproject.toml` / `package.json` / `Cargo.toml` / 自维护 `VERSION` 文件…，取运行时或打包实际读取的那一个）。若项目里有多处写了版本号（如 `__version__`、`setup.py`、文档头部），**只有这一处决定版本号**，其余都是需要同步的辅助信息（发版时一并改到同一版本号，不各自递进）；纯重复且无用时可以删除，或改成从版本源派生。

| 版本源文件 | 位置 |
|------|------|
| `{{ 版本号文件 }}` | 版本字段（运行时/打包实际读取的那一个） |

README 徽章、文档正文里的版本字样、i18n 文案等属于**辅助信息**：不决定版本号（以版本源为准），但**准备发布时必须同步到同一个新版本号**，不得残留旧版本号；日常提交不动它们，也不要新增此类重复版本号（需要展示版本时从版本源读取，不手写）。

#### 多会话并行开发（并行修改协议，适用于所有共享文件）

**触发条件**：只有出现下列情况才启用本节，否则按普通流程走，**不增加任何额外动作**——① 仓库里存在他人未提交或进行中的改动；② 用户明确要求并行工作；③ 任务板上存在他人 `in_progress` 任务，或与本会话写域重叠。

1. **先划写域**：动手前列出本会话要改的文件，与并行方比对；有重叠就**停下来问用户**，不自行决定谁先写。
2. **按冲突面选手段**：不同文件 → 直接并行；同模块下不同文件 → 各自分支、收口时合并；同一文件的同一区块 / 版本号 / schema 变更 → 指定**唯一写者**，其余排队等。
3. **共享单文件先认领**：改动前在任务板置 `in_progress`，或落 `.locks/<文件名>.lock` 写明会话与时间，写完即释放；未认领就改共享文件 = 违规。`.locks/` 只存本地、**不提交**，发版前清理。
4. **记录类文件只追加**：CHANGELOG / TODO / 注册表 / 路由表这类文件只做定位式追加，**禁止整文件重写**（整文件写回会连带盖掉他人条目）。
5. **收口单一 owner**：合并由一个会话执行，其他人只产出分支或 patch，不各自往主干合。
6. **提交前自查**：`git status --short` 确认只碰本会话写域内的文件；看到别人的改动就停下来问，不顺手清理。

**CHANGELOG 专项**（条目写法见上方「流程」与「写作视角」）：更新 `CHANGELOG.md` 前必须先读取当前文件内容，识别并保留其他会话已写入的既有条目（含 `[Unreleased]` 下未提交的内容），只追加自己的条目，**严禁整文件覆盖或删除他人记录**。边界：本条保护的是**仍然有效**的记录；条目已被撤销、或已在本次发版中并入版本段，可以删除或移动，但删除前须能说清「谁被撤销 / 归并到哪」，不得顺手清理看不惯的内容。
