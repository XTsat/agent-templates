# AGENTS.md — 通用项目模板

> 本文件是任何 AI 编码代理（agent）进入 **不适用专用模板的项目** 时的**必读**工作说明书。
> 它约定项目的目录结构、技术栈声明、代码规范、文档维护与提交流程。任何对代码、配置、行为的改动，都必须同时遵守本文档的规则。
>
> 适用项目：未命中 `astrbot-plugin`（AstrBot 插件）与 `nextjs-webapp`（Next.js Web 应用）专用模板的其它类型项目，例如通用 Python / Go / Rust 库、CLI 工具、脚本仓库、文档站、无框架前端、服务端 API 等。
>
> 本文档中所有 `{{ 占位 }}` 形式的内容，由 **agent 进入项目后第一件事填写**（读出项目实际技术栈，回填到本文档，替换占位标记）。
>
> **来源**：本文件是 [agent-templates](https://github.com/XTsat/agent-templates) 的 `templates/generic/AGENTS.md` 副本，最新版见该仓库 `main` 分支。
> 用户说「更新 AGENTS」时按此流程：① 拉取来源模板最新版 → ② 与本地逐节比对 → ③ 合并（保留本项目已回填的技术栈、目录结构与项目特有约定，**禁止把已填内容改回 `{{ 占位 }}`**）→ ④ 展示 diff 与改动清单，等用户确认后再落盘。**禁止整文件覆盖**。

## 4. 核心代码规范

### 4.1 命名约定

| 元素 | 约定 |
|------|------|
| 类 / 类型 | `PascalCase` |
| 文件 / 目录 | `snake_case`（JS/TS 生态允许 `kebab-case`，与相邻文件一致） |
| 函数 / 变量 | 语言惯例（Python `snake_case`，JS/TS `camelCase`），与现有代码一致 |
| 模块级常量 | `UPPER_SNAKE` |
| 私有成员 | `_` 前缀（Python）/ `#` 或模块内私有（JS/TS），不导出 |

### 4.2 类型与语法

- 函数签名**必须完整类型标注**（参数 + 返回类型）；类型标注无效的语言（如无类型系统的脚本语言）除外。
- 禁止 `Any` / `any` 作为类型标注（除非调用方签名强制要求）。
- 禁止无理由的类型忽略（`# type: ignore`、`@ts-ignore`、`@ts-expect-error`）。
- 严格模式优先：TypeScript 开 `strict`，Python 可用 `pyright`/`mypy` 时启用。

### 4.3 注释规范

- **注释只写 non-obvious reason**：解释「为什么这么做」，而不是「做了什么」（代码本身应自文档化）
  - 坏：`# 设置超时时间为30秒`（代码已写 `timeout = 30`）
  - 好：`# 30秒超时，因为上游API的SLA承诺P99为25秒`
- **禁止残留 intermediate attempts**：不保留被注释掉的旧代码、TODO 但未完成的方案、调试输出。
- 公开方法/函数写 docstring（中文）说明用途/参数/返回；用途足够明显的私有成员可省略。

### 4.4 日志

- 统一使用语言标准日志机制（`logging` / `console` 分级），按级别区分：`info` 常规、`warning` 可恢复问题、`error` 失败。
- **日志必须带模块/项目标识前缀**（如 `[{{ PROJECT_NAME }}]`），多模块项目含模块名。
- 错误上下文带关键入参（脱敏后），便于定位。

### 4.5 错误处理与防御性编程

- 外部输入必须校验并优雅 fallback（越界取默认、缺字段跳过），不因单条脏数据中断整体。
- 外部 IO / 网络调用必须 try/except 并记录日志，**不允许静默吞异常**。
- 精确捕获异常类型（`ValueError`、`TimeoutError`），禁止裸 `except:` / 空 catch（除非注释说明理由）。
- 降级链路清晰：首选方案 → 兜底方案 → 占位文本/明确的失败提示。

### 4.6 并发

- 异步 IO 用 `async/await` 或对应语言惯用法，**禁止阻塞事件循环 / 主线程**。
- 并发限制用信号量/并发原语，`finally` 中释放资源、取消未完成任务。
- 计算重活放线程池/子进程/worker，不在请求路径上同步执行。

### 4.7 数据与文件

- 读写文件统一 `utf-8`（除非格式另有规定），写操作持锁（如必要），**原子写入**：先写 `.tmp` 再 replace。
- 数据目录用标准位置（`$XDG_DATA_HOME` / 平台约定 / 可配置），禁止散落在仓库内写用户数据。

## 7. 文档维护规范（强制，不可省略）

> 本项目的**硬性要求**：任何改动在合并前，必须同步维护 `README.md` 与 `CHANGELOG.md`。未同步文档 = 任务未完成。

### 7.1 CHANGELOG 维护

#### 流程

- 日常改动先记在 `## [Unreleased]` 段（顶部固定）。**发版时**再把内容移动到带版本号的新段。
- 多个不相关改动在同一工作周期内，各自独立记入 `[Unreleased]`，**不要**合并为一条。
- **发版日期**：版本段日期 `(YYYY-MM-DD)` 填**当前日期**（以发版当天的系统时间为准）。

#### 格式

统一使用 **分组式**（与 scaffold 的 `CHANGELOG.md.template` 一致）：按分类用 `###` 子标题分组，条目用「标题 + 冒号 + 说明」，**仅重点条目/重点内容才加粗**：

```markdown
# Changelog

## [Unreleased]

> 一句话总结这个版本（可选）

### 新增
- 功能 A：说明
- **功能 B**：说明

### 修复
- 问题 C：说明

## v0.3.0 (2026-07-06)

> 一句话总结这个版本（可选）

### 新增
- 功能 D：说明
```

分组子标题分类：`新增` / `修复` / `变更` / `移除` / `性能`（只保留本次有内容的分类，无内容的分类不写空标题）。

**加粗规则**：条目默认不加粗；写 changelog 时先识别本次改动中的**重点改动**（核心新功能、重要修复、破坏性变更等），只对重点改动用 `**加粗**` 标题强调，其余条目一律不加粗。

**版本总结**：版本标题（`## [Unreleased]` / `## vX.Y.Z (YYYY-MM-DD)`）与分类子标题之间，可加一行 `> 引用` 形式的一句话总结（概括该版本/该批改动的主旨），可选，不强制。

#### 写作视角（面向使用者）

CHANGELOG 的读者是**使用者**（库的调用方 / CLI 用户 / 服务使用方），不是开发者。条目只写「使用者能感知到的变化」，不写内部实现：

- **写使用者视角的结果**：能做什么、输出/行为有什么不同、配置与默认值如何变化。
- **禁止内部实现细节**：模块与函数拆分、数据结构、算法、缓存与并发策略、日志埋点、依赖升级、重构过程，一律不写。
- **禁止出现代码标识符与文件路径**（如 `_load_config`、`src/core/parser.py`）；使用者直接接触的**命令名、参数名、配置项 key、公开 API 名**除外。
- **无使用者感知的改动不记入 CHANGELOG**：纯内部重构、格式化、注释与测试调整等，写了用户也读不懂、也用不上。
- 判断标准：使用者读完一条，能决定「要不要升级、升级后有什么不同」。

正反例：

```markdown
### 新增
- ✅ 支持 `--timeout` 参数：自定义请求超时时间，默认 30 秒
- ❌ 新增 `_load_config` 并引入 dataclass 缓存，重构参数解析链路

### 修复
- ✅ 修复缺少参数时命令直接崩溃的问题
- ❌ 修复 `except` 分支未捕获 `KeyError` 导致的 `finally` 泄漏
```

#### 版本号（准备发布时才确认）

- **日常开发不碰版本号**：只往 `[Unreleased]` 追加条目，版本源文件里的版本号保持原值；每个功能、每个修复各自是一次独立提交，提交里不带版本号变更，也不改辅助位置的版本字样。
- **准备发布时才确认并递增一次**：一次发版汇总了多个独立的功能/修复提交，等合并到指定版本、把 `[Unreleased]` 内容移入 `## vX.Y.Z (YYYY-MM-DD)` 的同一次操作里，才确认版本号（SemVer 见 8.2）、写进下方的**唯一版本源文件**、把辅助位置同步成同一个版本号并打 `git tag vX.Y.Z`。**不能每改一点就递增**——否则版本号会随提交次数突进，与实际发布节奏脱节。
- **唯一版本源**：`{{ 版本号文件 }}` 的 version 字段（`pyproject.toml` / `package.json` / `Cargo.toml` / 自维护 `VERSION` 文件…，取运行时或打包实际读取的那一个）。若项目里有多处写了版本号（如 `__version__`、`setup.py`、文档头部），**只有这一处决定版本号**，其余都是需要同步的辅助信息（发版时一并改到同一版本号，不各自递进）；纯重复且无用时可以删除，或改成从版本源派生。

| 版本源文件 | 位置 |
|------|------|
| `{{ 版本号文件 }}` | 版本字段（运行时/打包实际读取的那一个） |

README 徽章、文档正文里的版本字样、i18n 文案等属于**辅助信息**：不决定版本号（以版本源为准），但**准备发布时必须同步到同一个新版本号**，不得残留旧版本号；日常提交不动它们，也不要新增此类重复版本号（需要展示版本时从版本源读取，不手写）。

#### 多会话并行开发

**⚠️ 更新 `CHANGELOG.md` 前必须先读取当前文件内容**，识别并保留其他会话已写入的既有条目（含 `[Unreleased]` 下未提交的功能），只追加自己的条目，**严禁整文件覆盖或删除他人记录**。

### 7.2 README 维护

- **功能/介绍**：项目是什么、核心功能、特性列表、截图/演示。
- **快速开始**：安装、依赖、最小可用示例（放在 README 前部）。
- **配置**：配置项表格（配置项、类型、默认值、说明）。
- **其它**：命令行/API 说明、常见问题、贡献指南、许可证、鸣谢等。

#### 写作视角（面向使用者）

README 的读者是**使用者**（库的调用方 / CLI 用户 / 服务使用方），不是开发者。只写使用者能直接用到的东西：

- **该写的**：能做什么（能力清单）、怎么装、怎么配（配置表）、怎么用（命令/API 示例）、出问题怎么办（常见问题、前置条件与限制）。
- **不该写的**：实现原理与设计理念、架构分层与模块职责、算法与数据结构、内部调用流程、私有函数名/文件路径、性能优化手段、依赖内部实现。
- **代码只贴使用者要用的最小片段**：安装命令、CLI 用法、公开 API 调用示例；不贴内部实现代码。
- **技术细节翻译成使用者语言**：不写「用信号量限制并发」，写「并发上限（`--concurrency`），超出后排队」。
- 判断标准：使用者只读 README，就能独立完成安装 → 配置 → 使用 → 排障。

正反例：

```markdown
- ✅ 支持自定义请求超时时间（`--timeout`，默认 30 秒）
- ❌ 通过 `_load_config` 把参数解析成 dataclass，并用 `asyncio.Semaphore` 控制并发
```

#### 双语原则（仅当项目维护多语言 README 时）

- **中文为主（单向同步）**：中文版是**权威版本（源）**，英文/其它语言版跟随中文版。所有改动**先落中文版，再同步**；**禁止反向**——不得先改外文版再回填中文，不得用外文版覆盖中文版。
- 章节结构必须保持一致，新增章节所有语言版本都要加。
- 外文版使用地道翻译，**禁止**逐字机翻、禁止留下半翻译的句子。

#### 何时必须更新 README

| 改动类型 | 必须更新位置 |
|----------|-------------|
| 功能新增/删除 | 功能/介绍、命令/API 清单 |
| 使用方式/命令/API 变化 | 快速开始、命令/API 章节 |
| 配置项变化 | 配置章节 |
| 依赖/版本要求变化 | 快速开始（安装/依赖部分） |
| 已知问题/行为变化 | 常见问题部分 |

**何时不需要更新 README：**
- 纯内部重构（行为完全不变）、样式调整、bug 修复（除非修复改变了用户可见行为）。

#### 格式与多会话约束

- **禁止无意义的换行**：正文长句不要人为软换行（一段文字保持一行，由 Markdown 自动折行显示）；空行只用于分隔标题、表格、列表、代码块等结构性区块。
- **多会话并行修改**：更新 `README.md` 前必须先读取当前文件内容，识别并保留其他会话已写入的既有内容，只追加/修改自己的部分，**严禁整文件覆盖或删除他人记录**。

### 7.3 PR 描述规范

- **PR 描述只写最终行为**：描述最终完成了什么，而不是过程中尝试了什么。
- 禁止提及：尝试过的方案、被否定的设计、从未合入的中间状态。
- 只写 diff 里看不出来的取舍理由（如「选用方案A因为性能比B高20%」）。

## 8. 提交与发布流程

### 8.1 提交规范（Conventional Commits）

提交信息遵循 **Conventional Commits**，格式：

```
<type>(<scope>): <subject>
```

- `<type>` 用英文小写，可选：`feat`（新功能）/ `fix`（修复）/ `docs`（文档）/ `refactor`（重构）/ `perf`（性能）/ `test`（测试）/ `build`（构建）/ `ci`（CI）/ `chore`（杂务）/ `style`（格式）。
- `<scope>` 可选：受影响模块名（如 `config`、`cli`）。
- `<subject>` 用**中文短句式**描述最终行为，不带句号。
- 破坏性变更：`<type>!:` 或在正文写 `BREAKING CHANGE:` 说明。

示例：

```
feat: 新增超时配置项
fix(cli): 修复无参数时的崩溃
docs: 补充安装步骤
refactor: 重构配置加载逻辑
```

- **禁止**将未完成的功能、多轮迭代的中间状态、被废弃的方案写进提交信息。
- **提交前必须先向用户展示改动内容和提交标题**，等用户确认后再执行 commit。展示内容至少包含：待提交文件清单、改动概要（如 `git diff --stat`）、提交标题；涉及推送时另附提交 hash 与目标分支。其中的**提交标题尽量给 2–3 个候选**（同一改动的不同侧重点：做了什么 / 为什么改 / 是否带 scope），逐条注明侧重供用户挑选，并标出推荐项；确实只有一种合理写法时才只给一个，用户选定（或自拟）标题后才 commit。
- 推荐顺序：完成功能代码 → 跑通验证 → 更新 CHANGELOG 与 README → 提交。
- 文档更新与代码改动**在同一提交中完成**（不单独拆「补文档」提交）。
- 只有用户明确要求时才 commit / push。
- **授权一次性，不延续**（「上一轮说过推送」≠ 本轮可以提交）：
  - 用户的确认**只对当次动作生效**；下一次改动必须重新展示改动内容与提交标题，重新确认。
  - 展示后改动内容又变了（用户提了新要求、你又改了文件，哪怕只改一行），**原确认立即失效**，必须重新展示并再次确认。
  - 下列情形**都不算授权**：上一轮 / 上一个任务 / 上一个会话说过「提交」「推送」；会话恢复（resume / fork）后继承的历史授权；用户对功能或代码表示满意；用户正在讨论其它需求；用户未回复。
  - 授权范围逐项独立：确认 commit ≠ 授权 push；确认推送某分支 ≠ 授权后续继续提交或推送；确认一个提交 ≠ 授权 `--amend` 或追加提交。
  - 执行前自检：能指出用户**本轮**对**本次改动**的明确同意原话；指不出来就先问，不要执行。

### 8.2 版本号与发布

- 采用 **SemVer**：新功能 → `minor` 递增；bug 修复/小改进 → `patch` 递增。
- **只在准备发布时递增**（规则见 7.1）：单个功能/修复提交不碰版本号；一次发版汇总多个独立提交、合并到指定版本时才确认版本号，改 `{{ 版本号文件 }}` 的 version，并把 README 徽章、文档版本字样、i18n 等辅助位置同步到同一版本号——逐次递增会让版本号突进。
- 发版一致性：`{{ 版本号文件 }}` 的 version = CHANGELOG 新版本段号 = `git tag vX.Y.Z`，tag 推送同样需用户确认。

### 8.3 测试与验证

- 提交前必须运行第 3 章声明的验证命令：
  - 有构建/检查：`{{ 构建命令 }}`（或 `{{ 类型检查命令 }}`）
  - 有测试：`{{ 测试命令 }}` 通过
  - 无框架：至少跑通入口冒烟（`{{ 冒烟命令 }}`）
- 若项目已补充单测，改动后需保证测试通过。
