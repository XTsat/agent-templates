
- 依赖方向严格单向：入口 → 业务层 → 基础设施/工具层，底层不反向依赖上层。

- 单一职责：一个文件/模块只做一件事；公共常量放独立的 constants 模块，禁止散落硬编码。

## 4. 核心代码规范

### 4.1 命名约定

| 元素 | 约定 |
|------|------|
| 类 / 类型 | `PascalCase` |
| 文件 / 目录 | `snake_case`（JS/TS 生态允许 `kebab-case`，与相邻文件一致） |
| 函数 / 变量 | 语言惯例（Python `snake_case`，JS/TS `camelCase`），与现有代码一致 |
| 模块级常量 | `UPPER_SNAKE` |
| 私有成员 | `_` 前缀（Python）/ `#` 或模块内私有（JS/TS），不导出 |

### 4.2 类型与语法

- 函数签名**必须完整类型标注**（参数 + 返回类型）；类型标注无效的语言（如无类型系统的脚本语言）除外。
- 禁止 `Any` / `any` 作为类型标注（除非调用方签名强制要求）。
- 禁止无理由的类型忽略（`# type: ignore`、`@ts-ignore`、`@ts-expect-error`）。
- 严格模式优先：TypeScript 开 `strict`，Python 可用 `pyright`/`mypy` 时启用。

### 4.3 注释规范

- **注释只写 non-obvious reason**：解释「为什么这么做」，而不是「做了什么」（代码本身应自文档化）
  - 坏：`# 设置超时时间为30秒`（代码已写 `timeout = 30`）
  - 好：`# 30秒超时，因为上游API的SLA承诺P99为25秒`
- **禁止残留 intermediate attempts**：不保留被注释掉的旧代码、TODO 但未完成的方案、调试输出。
- 公开方法/函数写 docstring（中文）说明用途/参数/返回；用途足够明显的私有成员可省略。

### 4.4 日志

- 统一使用语言标准日志机制（`logging` / `console` 分级），按级别区分：`info` 常规、`warning` 可恢复问题、`error` 失败。
- **日志必须带模块/项目标识前缀**（如 `[{{ PROJECT_NAME }}]`），多模块项目含模块名。
- 错误上下文带关键入参（脱敏后），便于定位。

### 4.5 错误处理与防御性编程

- 外部输入必须校验并优雅 fallback（越界取默认、缺字段跳过），不因单条脏数据中断整体。
- 外部 IO / 网络调用必须 try/except 并记录日志，**不允许静默吞异常**。
- 精确捕获异常类型（`ValueError`、`TimeoutError`），禁止裸 `except:` / 空 catch（除非注释说明理由）。
- 降级链路清晰：首选方案 → 兜底方案 → 占位文本/明确的失败提示。

### 4.6 并发

- 异步 IO 用 `async/await` 或对应语言惯用法，**禁止阻塞事件循环 / 主线程**。
- 并发限制用信号量/并发原语，`finally` 中释放资源、取消未完成任务。
- 计算重活放线程池/子进程/worker，不在请求路径上同步执行。

### 4.7 数据与文件

- 读写文件统一 `utf-8`（除非格式另有规定），写操作持锁（如必要），**原子写入**：先写 `.tmp` 再 replace。
- 数据目录用标准位置（`$XDG_DATA_HOME` / 平台约定 / 可配置），禁止散落在仓库内写用户数据。

## 7. 文档维护规范（强制，不可省略）

> 本项目的**硬性要求**：任何改动在合并前，必须同步维护 `README.md` 与 `CHANGELOG.md`。未同步文档 = 任务未完成。

### 7.1 CHANGELOG 维护

#### 流程

- 日常改动先记在 `## [Unreleased]` 段（顶部固定）。**发版时**再把内容移动到带版本号的新段。
- 多个不相关改动在同一工作周期内，各自独立记入 `[Unreleased]`，**不要**合并为一条。
- **发版日期**：版本段日期 `(YYYY-MM-DD)` 填**当前日期**（以发版当天的系统时间为准）。

#### 格式

统一使用 **分组式**（与 scaffold 的 `CHANGELOG.md.template` 一致）：按分类用 `###` 子标题分组，条目用「加粗标题 + 冒号 + 说明」：

```markdown
# Changelog

## [Unreleased]

### 新增
- **功能 A**：说明
- **功能 B**：说明

### 修复
- **问题 C**：说明

## v0.3.0 (2026-07-06)

### 新增
- **功能 D**：说明
```

分组子标题分类：`新增` / `修复` / `变更` / `移除` / `性能`（只保留本次有内容的分类，无内容的分类不写空标题）。

#### 版本号联动

采用 **SemVer**：新功能 → `minor` 递增；bug 修复/小改进 → `patch` 递增。涉及功能新增/删除、行为变化、配置项变化时，**各处同步递增**：

| 位置 | 说明 |
|------|------|
| `{{ 版本号文件 }}` | 版本字段（`pyproject.toml` / `package.json` / `Cargo.toml` / 自维护 `VERSION` 文件…） |
| `CHANGELOG.md` | 发版时从 `[Unreleased]` 移入 `## vX.Y.Z (YYYY-MM-DD)` |
| `README.md` | 版本徽章 / 安装版本号（如有） |

纯修复/内部重构可只更新 `[Unreleased]` 条目，不递增版本号。

#### 多会话并行开发

**⚠️ 更新 `CHANGELOG.md` 前必须先读取当前文件内容**，识别并保留其他会话已写入的既有条目（含 `[Unreleased]` 下未提交的功能），只追加自己的条目，**严禁整文件覆盖或删除他人记录**。

### 7.2 README 维护

- **功能/介绍**：项目是什么、核心功能、特性列表、截图/演示。
- **快速开始**：安装、依赖、最小可用示例（放在 README 前部）。
- **配置**：配置项表格（配置项、类型、默认值、说明）。
- **其它**：命令行/API 说明、常见问题、贡献指南、许可证、鸣谢等。

#### 双语原则（仅当项目维护多语言 README 时）

- **中文为主（单向同步）**：中文版是**权威版本（源）**，英文/其它语言版跟随中文版。所有改动**先落中文版，再同步**；**禁止反向**——不得先改外文版再回填中文，不得用外文版覆盖中文版。
- 章节结构必须保持一致，新增章节所有语言版本都要加。
- 外文版使用地道翻译，**禁止**逐字机翻、禁止留下半翻译的句子。

#### 何时必须更新 README

| 改动类型 | 必须更新位置 |
|----------|-------------|
| 功能新增/删除 | 功能/介绍、命令/API 清单 |
| 使用方式/命令/API 变化 | 快速开始、命令/API 章节 |
| 配置项变化 | 配置章节 |
| 依赖/版本要求变化 | 快速开始（安装/依赖部分） |
| 已知问题/行为变化 | 常见问题部分 |

**何时不需要更新 README：**
- 纯内部重构（行为完全不变）、样式调整、bug 修复（除非修复改变了用户可见行为）。

#### 格式与多会话约束

- **禁止无意义的换行**：正文长句不要人为软换行（一段文字保持一行，由 Markdown 自动折行显示）；空行只用于分隔标题、表格、列表、代码块等结构性区块。
- **多会话并行修改**：更新 `README.md` 前必须先读取当前文件内容，识别并保留其他会话已写入的既有内容，只追加/修改自己的部分，**严禁整文件覆盖或删除他人记录**。

### 7.3 PR 描述规范

- **PR 描述只写最终行为**：描述最终完成了什么，而不是过程中尝试了什么。
- 禁止提及：尝试过的方案、被否定的设计、从未合入的中间状态。
- 只写 diff 里看不出来的取舍理由（如「选用方案A因为性能比B高20%」）。

## 8. 提交与发布流程

### 8.1 提交规范（Conventional Commits）

提交信息遵循 **Conventional Commits**，格式：

```
<type>(<scope>): <subject>
```

- `<type>` 用英文小写，可选：`feat`（新功能）/ `fix`（修复）/ `docs`（文档）/ `refactor`（重构）/ `perf`（性能）/ `test`（测试）/ `build`（构建）/ `ci`（CI）/ `chore`（杂务）/ `style`（格式）。
- `<scope>` 可选：受影响模块名（如 `config`、`cli`）。
- `<subject>` 用**中文短句式**描述最终行为，不带句号。
- 破坏性变更：`<type>!:` 或在正文写 `BREAKING CHANGE:` 说明。

示例：

```
feat: 新增超时配置项
fix(cli): 修复无参数时的崩溃
docs: 补充安装步骤
refactor: 重构配置加载逻辑
```

- **禁止**将未完成的功能、多轮迭代的中间状态、被废弃的方案写进提交信息。
- **提交前必须先向用户展示改动内容和提交标题**，等用户确认后再执行 commit。
- 推荐顺序：完成功能代码 → 跑通验证 → 更新 CHANGELOG 与 README → 提交。
- 文档更新与代码改动**在同一提交中完成**（不单独拆「补文档」提交）。
- 只有用户明确要求时才 commit / push。

### 8.2 版本号与发布

- 采用 **SemVer**：新功能 → `minor` 递增；bug 修复/小改进 → `patch` 递增。
- `{{ 版本号文件 }}` 的 version 与 `CHANGELOG.md` 最新版本必须一致。
- 发版时打 `git tag vX.Y.Z`，tag 推送同样需用户确认。

### 8.3 测试与验证

- 提交前必须运行第 3 章声明的验证命令：
  - 有构建/检查：`{{ 构建命令 }}`（或 `{{ 类型检查命令 }}`）
  - 有测试：`{{ 测试命令 }}` 通过
  - 无框架：至少跑通入口冒烟（`{{ 冒烟命令 }}`）
- 若项目已补充单测，改动后需保证测试通过。
