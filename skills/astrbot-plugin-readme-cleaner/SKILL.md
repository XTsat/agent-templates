# 用途

把 AstrBot 插件项目（`astrbot_plugin_*`）的 README 精简为「功能导向」文档：**只说明功能信息**（能做什么、怎么配置、怎么用、有什么限制），**不说明原理**（怎么实现的、内部机制、数据怎么存）。

参数：`TARGET`=插件项目目录（缺省为当前工作目录）。

# 核心判断标准

对 README 里每一条内容问一句话：**删掉它，用户还能不能正常使用这个功能？**

- 能 → 删。这是原理 / 内部细节，用户不需要知道。
- 不能 → 保留。这是功能信息：能力、配置、前置条件、限制、排障。

# 必须删除的内容类型（原理 / 内部细节）

1. **实现机制**：定时任务、轮询/重连、缓存、采样聚合、渲染/布局、同步流程等机制的具体参数与过程（间隔、上限、算法、实现方式）
2. **内部存储与路径**：数据目录结构、落盘文件名与格式、存储分片/裁剪规则、持久化位置（如 `data/plugins/...` 下的具体路径）
3. **算法内部逻辑**：降级取值链、响应解析规则、匹配/归类/过滤规则的完整推演（用户只需知道结果与可配置项）
4. **架构与目录结构章节**：README 里的项目文件树、分层架构说明（属于开发者文档，不是用户文档）
5. **重复解释**：同一件事在多节反复讲 → 只保留一处，其余删除
6. **冗余示例**：同一类示例有多个 → 保留一个代表性示例；若为配置所需映射表（别名表、ID 对照表、变量表），整表保留

# 必须保留的内容类型（功能信息）

1. **功能能力列表**：能做什么，每条 ≤ 2 行，只写能力不写实现
2. **前置条件与约束**（使用须知，不是原理）：需安装/依赖外部组件才生效、某平台或版本不支持某能力、某命令依赖特定服务
3. **指令表、自定义指令语法、配置项表**：配置表保留 配置名 / 类型 / 默认值 / 说明 四要素（配置名按「中文名（`key`）」格式），只精简说明列里的原理性长文，不删配置项本身
4. **部署步骤、版本兼容表、依赖清单**
5. **常见问题 / 注意事项**：保留用户会实际遇到的排障条目，每题压缩到 2–4 行结论
6. **用户需要主动做的配置提示**：在哪里调参数、需填什么地址、开启什么开关

# 执行流程

1. 读 `TARGET/AGENTS.md`（**存在则必读**）：确认项目文档纪律（头部规范、板块结构、CHANGELOG 要求，各项目可自定义）；缺失时以现状结构为准，**不得照搬其它插件的写法**
2. 读 `TARGET/metadata.yaml`：取 `display_name` / `desc` / `tags`，核对 README 头部与功能描述是否一致
3. 读 `README.md` 全文，按上文标准逐节重写，组织为通用板块：功能/介绍 → 指令 → 配置 → 其它（安装、依赖、FAQ 等）
4. **先落中文版，再同步英文版**：`README_en.md` 存在则必须同步（单向同步，内容一一对应）；不存在则不创建
5. 头部检查：h1、版本徽章、语言切换链接保持不变；不因文档瘦身改动版本号
6. `CHANGELOG.md` 顶部若无 `[Unreleased]` 段则补一段（固定标题），加一条「变更」分组条目：**精简 README**：功能介绍只保留功能说明，移除原理性描述，中英文版保持一致
7. 纯文档改动无需跑测试；收尾时核对 `<details>` 配对、表格列数一致、两份 README 章节结构对齐、正文无无意义空行/软换行

# 常见陷阱

- **不要删前置条件**：外部依赖、平台/版本限制决定用户要不要配置某开关，删了用户会误配
- **不要删配置项**：只删配置说明里的原理性长文；配置表是用户配置时的唯一依据
- **只改一份 = 任务未完成**：`README_en.md` 存在时两份必须同步
- **版本号/徽章不动**：README 精简是文档调整，不是功能变更
- **配置入口提示不能丢**：某功能的核心配置入口信息（在哪调参）被删后，用户会在配置表里找不到 → 必须留一行入口提示
- **不要带着某个插件的记忆套用**：每个插件的 README 结构、AGENTS.md 纪律可能不同，以目标项目自身为准
