# 模板编写细则

> 本文件是根 [`AGENTS.md`](../AGENTS.md) 的细则页：**模板正文怎么写**。
> 它不在自动注入范围内（候选文件名只有 `AGENTS.md`/`CLAUDE.md`/`AGENTS.local.md`/`CLAUDE.local.md`），需要时用 `read` 打开。
> 本文件上限 10 KB——`read` 工具单次返回上限 50 KB，超过就要分次读，模型会放弃。超限时按主题再拆一个文件，不要加长本文件。

---

## 一、每位模板的 `AGENTS.md` 必须包含的章节

为了让 agent 只读一个文件就能干活，每个模板的 `AGENTS.md` 建议固定以下章节顺序：

1. **项目概览** —— 这类项目是什么、核心能力、最小依赖。
2. **目录结构与架构** —— 标准文件清单 + 分层/依赖方向 + 各目录职责。
3. **技术栈与依赖** —— 语言版本、框架约束、禁止引入的依赖。
4. **核心代码规范** —— 命名、类型、注释/日志语言、错误处理、并发、防御性编程。
5. **配置与数据文件** —— schema、默认值、持久化位置。
6. **对外接口/命令清单** —— 若为插件，列指令表。
7. **文档维护规范** —— CHANGELOG / README 的**强制**同步规则。
8. **提交与发布流程** —— 提交信息的**内容标准**（type 选法、scope、subject 长度与写法、正文/footer、提交粒度）、push 是否需要确认、版本号在准备发布时确认递增。
9. **最终检查清单** —— 每次任务完成前的可勾选列表。

> 各模板可按类型增删章节，但这 9 块是「让 agent 拿起来就用」的底线。

## 二、模板编写规范

- **语言**：面向开发者的规范正文，默认中文；Web 应用模板中涉及用户可见文案的部分保留双语说明。
- **一致性优先**：模板正文统一约定，不保留历史差异。
- **禁止空话**：每个约定都要落到具体动作（「新增配置项 → 改这几处」而非「保持配置整洁」）。
- **提交前展示统一格式**：模板的提交规范必须把「展示三件套」写成独立的可勾选条目——待提交文件清单、改动概要（如 `git diff --stat`）、**2–3 个候选提交标题**（注明侧重与推荐项，用户选定后才 commit），并在最终检查清单里留一条对应项；禁止压缩成一句话塞在长段落里，否则派生项目更新 AGENTS 时会漏抄。
- **提交信息要有内容标准，不能只给格式**：模板的提交规范必须写清「每个字段该写什么」，并统一落到这几项（缺一不可）：① **type 选择表**——按「使用者得到什么」选（`feat` 新增可感知能力 / `fix` 修正可感知错误 / `docs` 纯文档 / `refactor` 无外部行为变化 / `perf` 可测量性能 / `test` / `build` / `ci` / `chore` / `style` / `revert`），并给出「不要用在哪」；② **scope** 取模块/页面名一个词，无归属就省略，禁止 `misc`/`update`/`all` 与文件名当 scope；③ **subject** 中文动宾短句、≤ 28 汉字、整行 ≤ 72 字符、只讲一件事、禁用「优化/完善/修复若干问题/更新文档」等空话；④ **正文**——**可选、不强制**，只在改动本身从 diff 看不出来时才写（取舍理由、需要使用者动手的迁移动作、破坏性变更），每行 `- ` 开头且 ≤ 5 条；只写与本次改动直接相关的内容，不写验证过程、影响面盘点、版本号递增流水、后续计划、过程与情绪，没有值得写的就留空；⑤ **footer** 承载 `BREAKING CHANGE` / `Refs` / `Co-authored-by`，issue 编号不进 subject；⑥ **提交粒度**——一个提交一件事、文档与代码同提交、不提交半成品与中间态；⑦ **正反例**与一条自查动作（`git log --oneline -10` 能否不看 diff 读懂）。只写「遵循 Conventional Commits」等于没写，agent 仍会随手造空话标题。
- **含示例**：关键格式（CHANGELOG 条目、metadata.yaml、命令表）必须给出最小可用示例。
- **文档面向用户**：模板中的 README / CHANGELOG 规范必须写明「面向用户」写作视角——只写用户能感知的能力、配置、用法与变化，禁止实现原理、架构分层、代码标识符与内部流程。**CHANGELOG 还要写「简洁」**：先记后合——记录时各改动独立记入、不预先合并，整理（提交或发版前）时把同一变化的多处调整合并成一条，不重复说明同一内容；条目只写相对上一版的变化（不复述仍然有效的旧功能，不写没有信息量的空话），一句话说清「做了什么 + 用户得到什么」，不加背景、动机与复杂形容。
- **来源可追溯**：模板顶部必须写明来源仓库与本文件的更新流程（拉取最新版 → 逐节比对 → 合并保留项目已回填内容 → 展示 diff 等确认），使派生项目里一句「更新 AGENTS」即可触发规范更新，且不会被整文件覆盖。
- **版本号只在准备发布时递增，发版时辅助位置一并同步**：模板必须指出**唯一版本源文件**（运行时/打包实际读取的那一个），由它决定版本号。日常改动一律不递增；一次发版往往汇总多个独立的功能/修复提交，只有合并到指定版本、准备发布时才确认版本号，**禁止在每次改动里都递增**（否则版本号会随提交次数突进，与实际发布节奏脱节）。README 徽章、正文版本字样、i18n 文案等辅助位置**不是版本源、不决定版本号，但发版时必须同步改到同一个新版本号**（不得残留旧号或自相矛盾），并且日常提交里不动它们、不要新增重复版本号（根 `README.md` 标题下的模板版本徽章除外，见「模板版本」条）。
- **模板版本：每个模板独立维护，推送前递增**：每个模板在自己的 `AGENTS.md` 头部维护一行 `> **模板版本**：vX.Y.Z（YYYY-MM-DD）`，该行就是**这个模板的唯一版本源**；三个模板各自编号、互不牵扯（`astrbot-plugin` 改动不给 `generic` 涨号）。**每次推送只要涉及模板内容，推送前必须递增对应模板的版本号**，档位默认取 `patch`：
  - `patch` +1（**默认，绝大多数修订走这档**）：规则条款的增删改、章节增删与顺序重排、`scaffold/` 骨架文件的常规调整、措辞与示例的修正——只要模板的约定方向没变，一律 `patch`。
  - `minor` +1（仅限大改动）：模板的章节体系重写、既有约定被推翻或改向、需要派生项目**动手迁移**才能跟上（如目录结构变化、必填配置新增、文件改名）。
  - `major`：暂不预设，留给模板定位整体重构；确需时另议。
  - 只改本仓库自身文件（根 `README.md`、根 `AGENTS.md`、`skills/`）→ 不递增。递增时把日期同步改为当天，并在推送前展示新版本号；同时把根 `README.md` 标题下对应模板的版本徽章改成新号（徽章是模板版本的辅助展示位，不决定版本号，但不许留旧号）。注意与上一条的分工：上一条约束的是**派生项目自己的产品版本**（发版才动），本条约束的是**模板版本**——模板一次推送就是一次发布，因为派生项目靠它判断要不要合并更新。
- **仓库 tag 只标重构点，不随每次版本递增**：日常的规则增删、措辞修正、示例调整都不打 tag——模板版本行已经记录了每一次变化（实测 `astrbot-plugin` 已走过 18 个版本），再给每个版本打 tag 只会让 tag 列表变成第二个版本号。只有**结构性重构**（如入口与 `docs/` 分离这类改变文件组织方式的改动）才打一个 annotated tag `v<版本>`，说明写清重构内容与派生项目的迁移动作。tag 指向**重构那次提交本身**，不随后续无关提交移动。
- **派生项目侧不改模板版本行**：模板头部的「模板版本」行随文件复制进派生项目，回填项目内容时**不得改动**；只有从上游合并到新版本时才把它更新为合并到的版本，并在合并说明里写出旧版本 → 新版本。
- **文档换行**：README / 模板正文禁止无意义的空行与软换行——HTML 头部区块内元素间不留空行，正文一段文字保持一行，空行只用于分隔标题、表格、列表、代码块等结构性区块。
- **双语以中文为主**：模板若维护双语 README，中文版为权威版本（源），改动先落中文版，再从中文同步到英文版，**禁止反向同步**。
- **多会话并行修改**：与其它会话同时改一个仓库时，先划写域——不重叠就各改各的；必须动共享单文件时先认领（任务板 `in_progress`，或落 `.locks/<文件名>.lock` 写明会话与时间，用完释放、**不提交**），只做定位式修改、**严禁整文件覆盖**；合并由单一 owner 收口；提交前 `git status --short` 自查只碰本会话写域。触发条件与档位划分见三份模板里的「多会话并行开发（并行修改协议）」。
